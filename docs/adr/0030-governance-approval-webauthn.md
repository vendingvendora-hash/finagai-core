# ADR-030: Governance approval authentication by WebAuthn

- **Date:** 2026-10-01
- **Status:** decided
- **Category:** architectural/security/authority change
- **Decided by:** Julian

## Decision

Every governance approval (ADR-019) requires, in order:

1. an authenticated browser session identifying Julian (approval-page sign-in through the identity provider, ADR-029);
2. a fresh WebAuthn ceremony with user verification required;
3. a challenge cryptographically bound to the governance request ID, its nonce, and its content hash, plus fresh per-ceremony randomness;
4. verification of the assertion by Core;
5. a re-check of every affected record's version and of the request's expiry;
6. atomic execution of the change;
7. an immutable audit event carrying the governance approval ID and the authenticated principal.

## Key custody

Julian's authenticator (device or platform passkey) holds the private key. Core generates challenges and verifies signatures. Core stores only public verification data: credential ID, public key, sign counter, transports, and the link to Julian's principal subject. Core never possesses, receives, or can reconstruct the private key.

## Challenge construction

`challenge = SHA-256("finagai-approval-v1" || request_id || nonce || content_hash || ceremony_random)`, where `ceremony_random` is 32 fresh random bytes. Core stores only a hash of the issued challenge with a 5-minute expiry, and accepts it once.

## Credential enrollment

The first credential is enrolled from an authenticated approval-page session plus a one-time enrollment code generated by the admin CLI on Julian's machine (never shown to Claude or sent through chat). Later credentials require an assertion from an existing credential. Revoking a credential sets `revoked_at`; revoked credentials can never verify.

## Security objective

Claude can propose an action but cannot produce the independent cryptographic proof required to authorize it.

## Consequences

- Schema: `webauthn_credential` table and challenge fields on `governance_request` (migration 0005).
- Implementation: M5, using a maintained WebAuthn server library; verification must check origin, RP ID, user-verification flag, challenge, and sign counter.

## Reversibility

Moderate: removing the requirement would weaken an approved authority control and requires Julian's approval.
