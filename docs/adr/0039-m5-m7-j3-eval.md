# ADR-039: M5 approval page, M7 seeding, J3 real-model evaluation harness

- **Date:** 2026-10-01 · **Status:** decided · **Category:** implementation of approved decisions (ADR-018, ADR-019, ADR-022, ADR-029, ADR-030) and reversible technical choices

## M5: governance approval page

- **Sign-in:** standard OIDC authorization code with PKCE, state, and nonce in a signed 10-minute cookie, requesting `prompt=login` and `max_age=0`; ID token verified with `jose` (issuer, audience = approval client, nonce); subject must equal `PRINCIPAL_SUBJECT`. Provider-neutral (ADR-029). The callback answers with a same-site link rather than a redirect so the `SameSite=Strict` session cookie is sent on the next request.
- **Enrollment:** the first passkey requires a one-time, 15-minute code minted by the admin CLI with the migration role (the app role cannot insert codes; verified by a schema test); later passkeys require an assertion from an existing passkey. Only public credential data is stored.
- **Approval:** the page shows exactly what will change. Challenge issuance fixes the per-ceremony random and the decision (approve or reject) server-side, so the browser cannot choose what the signature authorizes. The decision path verifies with the ADR-030 policy and then executes in one transaction that consumes the challenge, compare-and-sets the sign counter, re-checks every target version (stale means superseded, nothing applied), applies the action, and writes events carrying the approval ID and principal.
- **Executable actions:** proposal decisions (preferences and procedures become new versions), conflict resolution (keep existing, accept new, both valid, custom; due dates and titles on work items, claims on knowledge), archival, and seed-batch promotion. Other proposal kinds are refused, not guessed.
- **POST protections:** session cookie, same-origin `Origin` header, JSON body; bearer tokens are refused before the handler runs. The page has a strict content-security policy with per-response nonces.

## M7: seeding

- Sources run through normal J2 in `seeding` mode (sanitize-before-persist applies) with a required seed batch; all candidates are staged as `pending` with their proposed relation to live state.
- Consolidation merges exact duplicates inside the batch (provenance kept) and flags same-item date contradictions.
- Questions are generated by code, grouped by project: conflicts with existing records, conflicts inside the batch, unverified or missing dates, missing projects, duplicates, projects with no next action. Clear items are offered for bulk confirmation.
- Answers change staging only: confirm, reject, set a project, or set a due date in Julian's own words (parsed by code; unreadable dates are refused, never guessed).
- Promotion runs only inside the governance executor after Julian's WebAuthn-approved request. Confirmed items become live; conflicts with live state become conflict records (nothing overwritten); entities missing purpose or project stay staged (ADR-022); preferences and procedures become proposals with their own approval. A baseline J3 review runs automatically after promotion.
- A batch is capped at 400 staged items (small trustworthy state over volume).

## J3 real-model evaluation

- T11-T20 are defined with SQL fixtures (times relative to a fixed review moment) and deterministic assertions; each case and repetition runs in its own freshly migrated database on a disposable local Postgres.
- Every case has an implicit required check that the composed review is not degraded. Rubric criteria are graded by the grader model and reported, but are **not required** until Julian sets a qualitative threshold.
- Verdicts reuse ADR-038 (`safetyPassed`, `acceptancePassed`, exit code on acceptance). Each run has a spend cap (`EVAL_MAX_SPEND_USD`, default $5); runs skipped for budget are reported with their expected incremental cost and make acceptance fail.
- A local test validates every case with a faithful scripted composer, so fixture or assertion errors are caught before any paid run.
- Evaluation spend is metered in the per-case databases, not in production metering; the Anthropic workspace spend limit covers it.
